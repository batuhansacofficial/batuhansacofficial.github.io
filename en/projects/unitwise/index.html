01 / PROBLEM

The result,
with its context.

A unit converter needs to explain the units, formula, and rounding behind its result. When a value is invalid, the interface should show which field needs attention.

Unitwise addresses this across five conversion categories. Numeric operations and validation live in one service, keeping the web form and JSON API consistent.

02 / ARCHITECTURE

Two entry points,
shared rules.

Razor Pages processes the form on the server. A Minimal API exposes the same capabilities to programmatic clients. Both call the stateless ConversionService directly, without an HTTP call between them or a separate calculation layer.

  1. Form or JSONRazor Pages and the Minimal API pass requests to the shared service.
  2. ConversionServiceValidates input, units, and ranges; calculates and formats the result.
  3. UnitCatalogDefines units, factors, and defaults for all five categories.

JavaScript submits the form in the background and updates the panel rendered by the server; it performs no conversion arithmetic. The last five successful conversions stay in the browser, so history needs no server database.

03 / TECHNICAL DECISIONS

A small tool,
deliberate choices.

Rational intermediate values

BigInteger-based rational arithmetic preserves conversion factors until the final decimal result. Intermediate overflow therefore does not prevent a representable result from being calculated.

Calculation and display

The default display rounds to six decimal places. Small nonzero results use scientific notation, and an approximation sign appears when rounding changes the displayed value.

Numeric strings in JSON

value and inputValue are returned as strings to preserve decimal digits in JavaScript clients. formattedValue carries the separate presentation text.

An independent core flow

The form works with JavaScript disabled. History, clipboard access, and background updates are optional enhancements. If browser storage is unavailable, history lasts only for the current visit.

05 / VERIFICATION

Testing the rules
and entry points.

xUnit tests cover reference conversions, round trips between catalog units, temperature boundaries, culture-independent number parsing, and overflow. HTTP integration tests check the API contract, validation responses, native form submissions, and antiforgery protection.

GitHub Actions runs a Release build, tests, and coverage collection, then builds a Docker image and performs a smoke test as a non-root user. The CI run for the referenced source version is linked below.

Verified behavior: In the live application, 20 °C produces 68 °F with its formula. A −1 K input produces a field-specific validation error without presenting a valid conversion result.

06 / SCOPE AND LIMITS

A conversion tool
with explicit limits.

Results are limited to the .NET decimal range. Values too large or too small to represent produce validation errors. Inputs use a decimal point without grouping separators; scientific notation is also supported.

The “Weight” category represents mass, and volume units such as cups and gallons are labeled as US measures. Currency conversion, user accounts, and server-side history are outside the project's scope. The live demo may take time to wake up after its hosting service has been idle.
