01 / PROBLEM

An explicit API around an external service.

Passing a weather provider's response directly to the client ties the application to the provider's data structure and error behavior. My focus in this project was to map Visual Crossing data into consistent response models and expose current, forecast, and historical weather through three endpoints.

Redis caching handles repeated queries. City, day count, and date validation take place at the API boundary, while provider failures are translated into HTTP statuses the client can distinguish. Failure behavior becomes part of the contract alongside successful data retrieval.

02 / REQUEST FLOW

Check the cache, then call the provider.

  1. WeatherControllerValidates input and forwards the request through IWeatherService.
  2. WeatherService + RedisChecks the cache using a normalized query key.
  3. HttpClientCalls the provider through the resilience pipeline on a cache miss.
  4. Consistent JSON responseMaps the data to a response model, caches it with an expiry, and returns it.

FromCache identifies the response's source, while RetrievedAtUtc records when the data was retrieved. The provider's observation time is kept in a separate field. Cached data is not presented as a newly retrieved observation.

03 / TECHNICAL DECISIONS

Speed, freshness, and failure boundaries.

Cache lifetimes by data type

The absolute expiration limit is 10 minutes for current weather, 30 minutes for forecasts, and 12 hours for historical data. Separate sliding expiration periods are also used. This balances fewer provider calls with each data type's freshness requirements.

Continuing after Redis failures

A cache read or write failure does not prevent the provider path from returning a response. The tradeoff is that external service requests may increase when the cache is unavailable. Cancellation requested by the caller is propagated rather than swallowed as an error.

Bounded retries

The HttpClient pipeline includes retries with jitter, a per-attempt timeout, a total timeout, and a circuit breaker. The total limit is 20 seconds, with 8 seconds per attempt. The aim is to tolerate transient failures while preventing unbounded waits.

A consistent error contract

Validation failures, an unknown city, provider failures, and timeouts map to distinct HTTP statuses. The error body contains a status, message, trace identifier, and timestamp; unexpected internal error details are kept out of the response message.

05 / TESTING APPROACH

Behavior beyond successful responses.

The xUnit tests cover data mapping, cache use on repeated calls, invalid queries, malformed provider JSON, timeouts, and open-circuit behavior. Missing API keys and invalid provider addresses are also validated at startup. Separate resilience tests exercise the actual HTTP resilience pipeline configured through DI and the propagation of caller cancellation.

Application integration tests replace the provider with a controlled HTTP handler and the cache with an in-memory implementation. Passing these tests does not verify a live provider or an actual Redis connection.

The linked successful CI run in the source repository includes formatting checks, dependency auditing, a Release build, tests and coverage output, and a Docker Compose build on Linux.

06 / SCOPE

Local development and portfolio use.

This project explores how to keep external service access and application behavior within distinct boundaries. Local setup and Docker Compose instructions are available in the repository. Authentication and rate limiting are outside this version's scope, and no public API demo is provided.
